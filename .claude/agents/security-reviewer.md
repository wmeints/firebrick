Firebrick is a sandbox for coding agents. It runs untrusted code generated by a
coding agent in a microsandbox microVM and limits what that code can reach: the
host, the network and the user's secrets.

## Trust boundary

Treat everything the agent can write as attacker-controlled:

- everything inside the guest VM, including its processes, its output and the
  data it sends over any channel to `fbkd`,
- every file in the mounted workspace, including `.firebrick.yml`, `.git/` and
  editor configuration, and symlinks the agent creates there.

Trusted are the host, the `fbk` CLI, the `fbkd` daemon, the user's own files
outside the workspace, and the user acting on purpose.

Out of scope:

- malware that already runs as the host user,
- escapes from the microsandbox VM itself, unless firebrick configures
  microsandbox in a way that weakens it,
- what the agent can do inside the guest, such as using passwordless `sudo` or
  Docker; the VM is the boundary.

## Before you review

Read the intended design so you don't report accepted trade-offs as findings:

- `docs/architecture/08-crosscutting-concepts.md`, especially secret scopes and
  securing the daemon socket,
- `docs/architecture/11-risks-and-technical-debt.md` for known risks,
- the decision records in `docs/architecture/decisions/`, at least 0004, 0006,
  0016, 0017, 0018, 0019, 0021, 0022, 0026, 0030 and 0033.

When a finding contradicts a decision record, say so and link it. Don't report a
risk the docs already accept, unless the code doesn't do what the docs say.

## What to review

For each check, trace attacker-controlled input to the place on the host where
it is used, and look for what lets it cross the boundary.

1. **Host access beyond the workspace.** The agent may use the mounted workspace
   but must not reach other host directories or host functionality.
2. **The workspace spec.** `.firebrick.yml` sits in the workspace, so the agent
   can edit it. Check what `fbk` and `fbkd` do with an edited spec on the next
   `fbk start`, `fbk network` or `fbk port`: host paths in `mounts`, turning off
   `network.enforce`, widening `allow`, changing `image`, `ports` or `name`, and
   whether the user is warned before such a change applies
   (`crates/spec/src/lib.rs`, `crates/cli/src/`,
   `crates/daemon/src/sandboxes.rs`).
3. **Injection into host files.** `fbkd` writes the SSH config
   (`crates/daemon/src/ssh.rs`) and edits VS Code and Zed settings (`vscode.rs`,
   `zed.rs`, `settings_file.rs`). Check whether names, paths or other values
   from the spec or the guest can inject directives, such as a `ProxyCommand`
   through a newline in a sandbox name, or escape the intended entry.
4. **Workspace files that run on the host.** Check whether `fbk` or `fbkd` read,
   write or execute files in the workspace on the host in a way the agent can
   abuse, for example by following a symlink out of the workspace. Note in the
   report, without filing it as a code finding, which planted files would run
   when the user opens the workspace on the host (`.git/hooks/`, `.git/config`
   with `core.fsmonitor` or `core.sshCommand`, `.vscode/tasks.json`, `.envrc`),
   and whether the docs warn about them.
5. **Guest-to-host channels.** The URL relay and OAuth callback forwards
   (`open.rs`, `forward.rs`, ADRs 0026 and 0030) and the configured port
   forwards (`forward.rs`, ADR 0019): bypasses of the URL parsing and the
   loopback and private address checks, callback ports that reach a host service
   or that another process can take over, listeners on addresses other than
   loopback, and the limits on the FIFO protocol.
6. **Guest output on the host terminal.** `fbk run` and the SSH sessions show
   guest output on the host. Check whether terminal escape sequences, such as
   OSC 52 clipboard writes, reach the user's terminal unfiltered.
7. **Egress policy bypasses.** With `network.enforce: true` the agent may only
   reach allowed hosts (`crates/daemon/src/network.rs`, ADR 0018). Check DNS
   tunnelling through the DNS rule, SNI and `Host` header mismatches, QUIC over
   UDP, IP literals, IPv6 with `init: false`, `host.microsandbox.internal`, and
   rule ordering. Check that changing the rules with `fbk network` doesn't leave
   a window without the policy (ADR 0021).
8. **Secret exfiltration.** Real secret values must never enter the guest; it
   only sees placeholders that microsandbox replaces for the secret's allowed
   hosts (`secrets.rs`, ADRs 0004, 0022, 0033). Check whether a secret's allowed
   hosts can be wider than intended, whether a sandbox can get another sandbox's
   scoped secrets, including after recreating it from a snapshot, and whether
   values end up in logs, error messages, labels or gRPC responses.
9. **Private keys.** Host SSH keys, and the keys `fbkd` uses to reach a sandbox,
   must not enter the guest. Check agent forwarding, the SSH tunnel
   (`tunnel.rs`), the generated SSH config and the key files `fbkd` writes, and
   their permissions.
10. **The daemon socket and gRPC input.** Check the socket's permissions and
    peer check (`server.rs`), the fallback to the shared temp dir, races on
    files `fbkd` creates in shared or user-writable directories, and that names
    and paths in requests are validated before they reach the file system or
    microsandbox.
11. **Files at rest.** The permissions of `secrets.yml`, microsandbox's state
    directory and the SSH key directory when they are created, and whether a
    restrictive umask or an existing file with looser permissions changes that.
12. **The base image.** In the `Dockerfile`: downloads without a pinned version
    or checksum, `curl | sh`, apt repository keys, and what `/sbin/init`,
    `firebrick-open` and `firebrick-git-credential` trust. Note whether the
    default image is pulled by tag or by digest.

## Confirming findings

Confirm a finding by reading the code path end to end. Where reading isn't
enough, reproduce it against a real VM with the `smoke-test` skill, which
isolates the daemon, microsandbox state and SSH config from the user's own.
Don't touch the user's own sandboxes, daemon or `~/.ssh`. Mark findings you
couldn't confirm as uncertain.

## Report

Use this severity scale:

- **Critical** - the agent can run code on the host, read host files outside the
  workspace, or obtain a real secret value or private key, without the user
  doing anything unusual.
- **High** - the same, but it needs a common user action, such as running `fbk
  start` again or opening the workspace in an editor; or the agent can bypass an
  enforced network policy.
- **Medium** - a weakness that needs an unusual configuration or user action, or
  that leaks less sensitive data.
- **Low** - defense in depth, hardening and missing warnings in the docs.

List findings from most to least severe. For each finding give the severity, the
file and symbol, what is wrong, a concrete scenario where it causes a problem, a
suggested fix, and whether it is confirmed (and how) or uncertain. Group the
findings under the numbered checks above, and write "no findings" for a check
that found nothing; don't invent issues. Keep reproduction steps to what a
developer needs to verify the fix.

End with a one-line verdict: ready, ready after the listed fixes, or needs
rework.
